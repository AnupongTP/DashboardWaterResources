## 2. เหตุผลที่ใช้ฐานโค้ดปัจจุบัน

ระบบจริงใช้ `site/index.html` สำหรับจังหวัด และ `site/authority.html` ร่วมกับ
`site/assets/authority-app.js` สำหรับ 29 อปท. และ 4 อำเภอ
ข้อมูลผ่าน WaterData, API/version, IndexedDB และ adapters/responsibility mapping ที่มีอยู่

ไฟล์อ้างอิงทั้งสามมีข้อมูลฝังใน HTML และโค้ดทำงานต่างจากระบบจริง ตัวอย่างเช่น:

- ตัดรายการซ้ำ และทำเครื่องหมายไม่นับปริมาตรบางรายการ
- ตัวกรองกลางและแท็บ/ชุดวิเคราะห์ที่ระบบหน้าลิงก์แยกไม่ได้ใช้
- ไม่มีการผูกกับ route/data adapters ปัจจุบันแบบเดียวกับระบบจริง
- โหลด Google Drive แบบลองหลาย URL อัตโนมัติ
- ตั้งค่าคลัสเตอร์และตัวนับผู้เข้าชมต่างจากระบบปัจจุบัน

จึงนำมาใช้เฉพาะภาษาภาพและการจัดวางที่ใช้กับส่วนเดิมได้ ไม่คัดลอกข้อมูลหรือ business logic

## 3. ทางเลือกและข้อแลกเปลี่ยน

| ทางเลือก | ข้อดี | ข้อจำกัด | ข้อสรุป |
|---|---|---|---|
| 1. เปลี่ยนธีมอย่างเดียว | กระทบ DOM และ interactions น้อยที่สุด | รูปแบบการจัดวางยังต่างจากตัวอย่างมาก | พิจารณาแล้ว แต่ไม่ได้เลือก |
| 2. เปลี่ยนธีมและจัดวางอย่างจำกัด | ใกล้ตัวอย่างขึ้น และยังใช้ controls/modules เดิม | ต้องตรวจ selectors, ขนาดแผนที่, responsive และ interaction parity | ผู้ใช้เลือก |

การนำไฟล์ตัวอย่างมาทับทั้งไฟล์ไม่ใช่ทางเลือกที่ใช้ได้ เพราะขัดกับเงื่อนไขให้ฟังก์ชันและตัวเลขเดิมคงอยู่

### 4.1 ชื่อโครงการ

**KwanKukkeb – Phayao Water Resources Data Center Dashboard**

ปรับ brand heading ไทย/อังกฤษของหน้าจังหวัดและ template หน้าลิงก์แยก
ปรับชื่อแท็บจังหวัดที่มีชื่อเดิม ส่วนชื่อแท็บ อปท./อำเภอยังคงบอกชื่อพื้นที่ตาม URL
ชื่อหน่วยงาน/อำเภอใน `authorityHeading` ยังสร้างจาก context เดิม ไม่ใช้ชื่อแม่กา/แม่ใจคงที่จากตัวอย่าง
ไม่เพิ่มการแปลชื่อ อปท. ทั้ง 29 แห่งเป็นภาษาอังกฤษในงานนี้

### 4.2 ลักษณะภาพที่นำมาจากตัวอย่าง

- หัวเว็บไล่สีม่วง–น้ำเงิน พื้นหลังอ่อน และการ์ดสีอ่อนตามหมวด
- การ์ดมุมโค้ง เส้นขอบ/เงาบาง ปุ่มอ่านง่าย และระยะห่างสม่ำเสมอ
- หัวข้อใช้ลักษณะฟอนต์แบบ Prompt ตามตัวอย่าง เนื้อหาใช้ Sarabun พร้อม fallback ที่อ่านไทยได้
- ใช้สีแบรนด์กับส่วนตกแต่ง; คงความหมายสีสถานะ ความเสียหาย ประเภทแหล่งน้ำ และ legend เดิม
- รักษาปุ่มล้างตัวกรองสีน้ำเงินที่ใช้อยู่ และคงข้อความ/หน้าที่เดิม
- focus, active, disabled และ selected ต้องเห็นชัด; ใช้ได้ด้วย keyboard และ touch
- ไม่จำเป็นต้องนำ animation/เอฟเฟกต์ทุกชิ้นจากตัวอย่างมาใช้ และต้องเคารพ reduced motion

รายละเอียด shade, radius, spacing และน้ำหนักฟอนต์เป็นข้อเสนอให้ผู้ลงมือกำหนดจาก reference
โดยตรวจทั้ง desktop/mobile ไม่ตีความว่าเป็นค่าตัวเลขที่ผู้ใช้ระบุไว้แล้ว

### 4.3 ขอบเขตของการจัดวางใหม่

หน้าจังหวัด:

- คงการสลับบทสรุปผู้บริหาร/รายละเอียดข้อมูลและแท็บย่อยที่มีอยู่จริง
- จัดหัวเว็บ ตัวกรอง การ์ด KPI และกลุ่มแสดงผลเดิมให้เป็นระเบียบตามธีมตัวอย่าง
- ปรับ grid, ความกว้าง, spacing และตำแหน่งภายในกลุ่มเดิมได้
- คงตัวกรองอำเภอ/อปท./ตำบลและ combobox เดิม แม้ไฟล์อ้างอิงไม่มีบางตัว
- ไม่รวมตัวกรองที่เดิมทำงานแยกกันให้เป็น global state ใหม่

หน้า อปท./อำเภอ:

- คงหัวข้อพื้นที่ ตัวกรอง 5 KPI แผนที่ ตาราง 3 กราฟ และ DSS ตามส่วนที่ระบบปัจจุบันมี
- จัดกลุ่มหัวเว็บ/ตัวกรอง, KPI/insight, แผนที่/ตาราง, กราฟ และ DSS ให้เป็นชุดที่อ่านต่อกันได้
- Desktop ให้แผนที่/ตารางอยู่ร่วมแถวเมื่อพื้นที่พอ; mobile เรียงส่วนเดิมในลำดับการอ่านที่ชัดเจน
- ปรับ styling และการจัดเรียงภายในกลุ่ม ไม่เพิ่มแท็บคลังภาพหรือชุดวิเคราะห์จากหน้าตัวอย่าง
- ยังใช้ template เดียวสำหรับทุก slug ไม่มี HTML แยก 33 สำเนา

กติกาการจัดวางร่วม:

- คง ID, data attributes, controls และ event bindings ที่โค้ดใช้
- ไม่ย้ายหรือสร้าง Leaflet map, canvas หรือ popup DOM ใหม่ขณะใช้งานเพื่อทำ layout
- การเปลี่ยนขนาดใช้ workflow invalidateSize/resize เดิมที่แก้ไว้ ไม่แก้คลัสเตอร์หรือ popup เพื่อให้เข้ากับภาพ
- ถ้าใส่ wrapper จำเป็น ต้องตรวจ selectors ที่อาศัย parent/child, fullscreen target และ stacking context
- การเลื่อนแนวนอนในตาราง/กราฟที่ตั้งใจไว้ทำได้ แต่ทั้งหน้าต้องไม่ล้นขอบจอ

## 6. สถาปัตยกรรมที่เสนอให้ผู้ลงมือใช้

ใช้ HTML/CSS/JavaScript และ Leaflet/Chart.js/MarkerCluster เดิม ไม่เพิ่ม framework หรือ build system

ข้อเสนอของผู้ออกแบบ:

- เพิ่ม stylesheet ธีม เช่น `site/assets/dashboard-theme.css` โหลดหลัง styles เดิม
- ใช้ token ร่วมสำหรับแบรนด์ พื้นหลัง การ์ด ระยะห่าง และ typography
- แยก selectors สำหรับหน้าจังหวัดและหน้า scoped ให้ชัด เพื่อไม่ให้ styles ข้ามไปหน้า Mae Ka เดิม
- เปลี่ยน HTML เท่าที่จำเป็นสำหรับ wrappers/labels/classes โดยคงองค์ประกอบที่โค้ดทำงานอ้างอิง
- JavaScript ทำงานเดิมเป็นฐาน; ไม่คัดลอก script จาก reference

ชื่อไฟล์/รายละเอียด selector เป็นทางเลือกให้ผู้ลงมือปรับได้ หากยังคงขอบเขตข้างต้น
หากพบว่าต้องเปลี่ยน state model, routing, สูตร, adapter หรือการทำงานของตัวกรอง ให้หยุดเสนอแยกก่อน

ไฟล์ที่คาดว่าจะเกี่ยวข้อง: `site/index.html`, `site/authority.html`, stylesheet ใหม่ และ tests/screenshots ที่เกี่ยวกับ UI
ไม่วางแผนแก้ Netlify Functions, Blobs, Apps Script, credentials หรือ Production data

## 7. การพิสูจน์ว่าฟังก์ชันคงเดิม

ก่อนลงมือให้เก็บ baseline ของโค้ดปัจจุบัน และใช้ fixtures เดียวกันทดสอบก่อน–หลัง
แยกหลักฐานการเทียบภาพออกจากผลการทำงาน ไม่ใช้จำนวน Production ในอดีตเป็นค่าคาดหวัง

เกณฑ์ผ่าน:

1. record IDs และผล KPI/กราฟ/ตัวกรองตรงกับ baseline สำหรับ state เดียวกัน
2. ทุกส่วนเดิมยังเข้าถึงได้ด้วยการกดและ touch ไม่ได้เพียงซ่อนด้วย CSS
3. ทุกเส้นทาง อปท. 29 แห่งและอำเภอ 4 แห่งยังล็อกพื้นที่ถูกต้อง; invalid/stale data ถูกปฏิเสธตามเดิม
4. popup บนมือถือไม่ปิดเอง; หมุดพิกัดซ้อนกางเลือกได้; ย่อ/ขยายแผนที่และแสดงรูปเหนือแผนที่ได้
5. ไม่มีคำขอรูปซ้ำที่เพิ่มจากการ render/layout และ fallback ยังเกิดจากผู้ใช้ตามเดิม
6. counter identity/guards คงเดิม และไม่ส่ง hit จริงระหว่างทดสอบ
7. ไม่มี JavaScript page errors หรือ body overflow ที่เกิดใหม่
8. ชื่อใหม่ถูกต้องทั้งไทย/อังกฤษ และหัวข้อพื้นที่ยังถูกต้องตาม route
9. หน้า Mae Ka เดิมยังผ่าน regression และไม่ได้โหลดธีมใหม่

## 8. ขอบเขตที่ไม่ทำและข้อจำกัด

- ไม่เพิ่มฟีเจอร์ที่มีเฉพาะใน reference เช่น global filters ใหม่, deduplication, analytics ใหม่ หรือ gallery ใหม่ใน scoped pages
- ไม่ทำให้หน้าลิงก์แยกมีชุดฟังก์ชันแบบหน้าจังหวัด หากหน้าปัจจุบันไม่มี
- ไม่แก้พิกัดที่ซ้ำหรือสรุปว่า record ซ้ำกันจริงจากพิกัดอย่างเดียว
- ไม่เปลี่ยนข้อมูลที่อ่านจาก Production ให้เป็นข้อมูลฝังในไฟล์
- ไม่รับประกันแก้ HTTP 429/403 หรือสิทธิ์ Google Drive ด้วยงาน UI นี้
- ไม่ commit/push/deploy การปรับ UI ในขั้นออกแบบนี้; การอนุมัติแนวทางไม่ใช่การสั่งเผยแพร่
